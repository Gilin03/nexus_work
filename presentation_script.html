먼저 관제 화면 상단 스위치가 '방어 모드 OFF오프'인 취약 상태에서 공격을 진행하겠습니다.
공격자가 환경설정 파일(/.env슬래시 닷엔브)을 찔러보는 상황을 PowerShell파워셸에서 실행하겠습니다."

"터미널을 보시면 404 Not Found사공사 낫 파운드가 출력되었습니다. 공격자가 눈치채지 못하도록 평범한 404 에러로 위장 응답한 것입니다.

(강조) 하지만 보시는 것처럼 취약 모드에서는 IP가 차단 목록에 올랐어도 실제 서버 방어가 꺼져 있기 때문에, 공격자가 포털 페이지에 그대로 접속이 가능합니다.

[2단계: 방어 모드 ON 전환 및 403 즉시 차단 실증]
이제 관제 화면 상단의 '방어 모드 ON온' 스위치를 켜겠습니다. 0.1초 만에 시스템 전체에 방어가 가동됩니다.
이 상태에서 방금 차단된 공격자 IP로 포털 페이지 재접속을 시도하겠습니다.
보시는 것처럼 즉시 403 Forbidden사공삼 포비든이 발생하며 페이지 접속이 전면 차단되어 더 이상 들어가지지 않습니다!

보안 감사 로그(/admin/audit어드민 오딧)에도 ip_blocked아이피 블록트 판정(BLOCK블록)으로 명확히 기록되었습니다.
원클릭으로 [차단 해제]하여 정상 복구하는 것까지 확인했습니다. 이어서 김태빈 님의 404 경로 스캔 시연으로 넘기겠습니다."

💡 시연 필수 체크: 관제 브라우저는 192.168.3.14(화이트리스트 보호됨)에서 띄우고, 공격 curl컬은 192.168.3.11(차단 가능 타깃)에서 실행하여 관제자 자가 차단을 방지합니다.

02 · 개념 (왜 데모 스위치와 무관한가 — 디코이 vs 권한 방어 대조) ⏱️ 45초
🖥️ 슬라이드 화면 텍스트 (서식 100% 일치):
• "R1·R2·R8(디코이 IP 차단)은 SECURITY_MODE 토글로 제어됩니다. 취약 모드(OFF)에서는 IP 차단 후에도 접속되지만, 방어 모드(ON)에서는 403으로 차단됩니다. 반면 R9(비인가 관리자 경로)·R10(IDOR·기밀 접근)은 관리자 권한 체크·역할 체크·리소스 범위 체크가 토글 변수를 아예 참조하지 않는, 서버 측에 항상 고정된 검사이기 때문에 데모 모드로도 끌 수 없습니다."
• 하단 3대 기둥: 🪪 역할 기반 접근 제어(auth.py) · 🛡️ 관리자 전용 라우트 가드(admin.py) · 🗂️ 리소스 범위 검증(hr.py)
🎙️ 구두 발표 대본 (슬라이드 21번 핵심 개념 설명)

"22페이지는 시스템의 핵심 개념인 '왜 방어 모드 스위치와 무관하게 뚫리지 않는가'입니다.
슬라이드 상단 요약문처럼, R1알원 브루트포스나 R8알에이트 디코이 IP 차단은 토글 스위치로 제어됩니다. 1부 시연에서 직접 보셨듯이 취약 모드(OFF오프)에서는 IP가 차단 목록에 올라도 페이지 접속이 유지되지만, 방어 모드(ON온)에서는 즉시 403사공삼으로 전면 차단됩니다.

하지만 제가 구현한 R9알나인(관리자 권한)과 R10알텐(IDOR아이도어·기밀 통제)은 스위치를 OFF오프로 꺼도 절대로 뚫리지 않습니다.
그 이유는 auth.py의 역할 검사, admin.py의 관리자 가드, hr.py의 리소스 소유권 검사가 토글 변수를 아예 참조하지 않고, 서버 백엔드 로직 자체에 '항상 고정된 불변의 룰'로 박혀 있기 때문입니다."

💡 강조 포인트: 슬라이드의 보라색 강조 문구(관리자 권한 체크·역할 체크·리소스 범위 체크가 고정된 검사)를 손으로 짚으며 R9/R10의 불변성을 확신 있게 발언합니다.
